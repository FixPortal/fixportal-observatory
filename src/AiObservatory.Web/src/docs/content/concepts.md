# Concepts

This page defines the model behind every figure in Observatory: source, scope and basis, the different kinds of money value, the difference between `Not reported` and zero, and why totals are never mixed.

## Source, scope and basis

Each usage observation answers three questions. The screens show the answers as columns, labels and legend entries.

| Question                          | Field                                   | Where you see it                                                                                          |
| --------------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Where did it come from?           | Source (`sourceId`, plus a source kind) | The `Source` column of the Model breakdown; the legend of the `Usage value` chart; the Data sources panel |
| What kind of use is it?           | Scope (`usageScope`)                    | The `Scope` column; the chart legend                                                                      |
| How was its money value obtained? | Basis (`costBasis`)                     | The `Basis` column; the chart legend; which summary card the value lands in                               |

Provider is a fourth, plainer label: which vendor's model was used (`Anthropic`, `OpenAI`, `Copilot`, `Google`, `Moonshot`, `xAI`, `Meta`, `z.AI`, `DeepSeek`). Unknown providers are shown with a tidied version of their key.

### Source kind

The source kind says what sort of system produced the observation. The API returns it, and the screens use it indirectly through the source name.

| Value            | Meaning                                                                                            |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| `providerApi`    | A usage, cost or reporting API operated by the provider.                                           |
| `localTelemetry` | Data read from a CLI, session or transcript on a machine.                                          |
| `manual`         | An observation a person entered.                                                                   |
| `synthetic`      | Demonstration data generated by Observatory. It is never evidence from a provider or a local tool. |
| `legacy`         | Retained data whose original source could not be recovered safely.                                 |

### Scope

| Label in the UI | Value          | Meaning                                                        |
| --------------- | -------------- | -------------------------------------------------------------- |
| API             | `api`          | Pay-as-you-go or contracted API consumption.                   |
| Subscription    | `subscription` | Allowance or activity under a consumer or team coding product. |
| Mixed           | `mixed`        | An upstream source explicitly combines scopes.                 |
| Unknown         | `unknown`      | The scope cannot be established.                               |

### Basis

| Label in the UI     | Value               | Meaning                                                                                        | Summary card                           |
| ------------------- | ------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------- |
| Billed              | `billed`            | Provider-reported financial cost or ledger evidence.                                           | `Billed spend` (from the spend ledger) |
| Provider estimate   | `providerEstimated` | A provider-produced estimate. It is not an invoice.                                            | `Provider estimate`                    |
| List-price estimate | `listPriceEstimate` | Tokens rated against an observed public price catalog.                                         | `List-price estimate`                  |
| Notional            | `notional`          | An API-list-price comparison for subscription or local activity, where no money changed hands. | `Subscription notional`                |
| None                | `none`              | Usage is reported but no price applies.                                                        | None                                   |
| Unknown             | `unknown`           | Legacy or insufficiently described cost.                                                       | None (see the note below)              |

A cost that sits under a basis the cards do not categorise is not dropped silently. The Overview shows a note that says how much was reported under such a basis and points to the Model breakdown. See [Overview](/docs/overview#unclassified-cost-note).

## Four kinds of money value

The same tokens can be valued four ways. Observatory keeps them apart because they mean different things.

| Value                 | What it is                                                                                                                                  | Money changed hands?                             | Where it appears                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------- |
| Billed spend          | Charges and credits recorded in the spend ledger, from provider billing sources, feeds or manual entries. Credits and refunds are negative. | Yes                                              | `Billed spend` card, Reporting, Spend             |
| Provider estimate     | A cost the provider calculated and reported, such as a per-session cost recorded by a CLI.                                                  | Not necessarily invoiced                         | `Provider estimate` card                          |
| List-price estimate   | API usage priced from public list prices at the time of use.                                                                                | Only if the usage was billed per token elsewhere | `List-price estimate` card                        |
| Subscription notional | What subscription or local activity would have cost at API list prices.                                                                     | No                                               | `Subscription notional` card, Subscriptions panel |

Notional value is a comparison, not spend. A subscription is a flat fee; the notional figure tells you how much of the plan you used, valued at list prices. See [Subscriptions](/docs/subscriptions).

The pricing catalogs and the way events are rated are in [Pricing](/docs/pricing).

## Not reported versus zero

A missing value is never shown as zero. Observatory distinguishes three situations.

| Situation                                       | What the UI shows |
| ----------------------------------------------- | ----------------- |
| Usage was recorded but the source gave no cost  | `Not reported`    |
| The source says no price applies (basis `None`) | A known zero cost |
| A cost exists and is zero                       | `£0.00`           |

How "no cost" is tracked:

- Every daily aggregate carries `requestCount` and `unknownCostCount`. The second is the number of requests in the aggregate whose cost the source did not report.
- A figure counts as reported only if `requestCount` is greater than `unknownCostCount`. Otherwise the card, table cell or chart shows `Not reported`.
- A partly reported figure shows its known subtotal with a qualifier, for example `3 observations not reported`. The subtotal is real; the qualifier tells you it is incomplete.
- Cache savings follow the same rule with their own unknown count.

Tokens follow the same principle. A card with no aggregates at all reads `Not reported` rather than `0`.

> A cost under basis `None` is a known zero because no price applies. It is not the same as a missing cost. The Model breakdown shows such a row's cost as `£0.00`.

Adversarial review runs have their own version of this rule: a run whose panel cost could not be established is stored with a zero placeholder and a flag, excluded from average-cost figures, and shown as `Unknown`. See [Adversarial Review](/docs/adversarial-review).

## Time: when it happened, when it was seen, when the source last worked

Three different times are kept apart.

| Time                | Meaning                                                                                                                                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Occurrence time     | When the consumption happened. Daily aggregates are grouped by this date.                                                                                                                                |
| Observed time       | When Observatory obtained the observation. A backfill can be observed long after it occurred.                                                                                                            |
| Source status times | Per source: the last attempt, the last success and the latest observation the source supplied. The Data sources panel shows the last success; `Not reported` there means the source has never succeeded. |

Freshness is a property of a source, not of a figure. The Data sources panel classifies each source from these times. See [Data sources](/docs/data-sources).

## Currency

- Estimates, notional values and stored catalog prices are in US dollars. The dashboard converts them to pounds for display using a live USD to GBP rate that the browser fetches and caches for about 12 hours. If the rate service cannot be reached, the dashboard uses a fixed fallback rate of 0.79, so a figure shown during an outage uses that rate. The conversion uses the current rate, not the rate on the day of the usage.
- Billed ledger entries are different. Each entry stores the amount as charged, its currency, and a GBP amount and FX rate that are converted once when the entry is written, using the rate on the entry's date, and not recomputed. Billed totals sum those frozen GBP amounts, so a later move in the exchange rate does not change a past entry.
- Subscriptions are priced in GBP or USD. USD prices are converted at the live rate when they are compared with notional usage.
- Token values are counts.

## Provenance and identity

Observations are source-scoped. A usage event is identified by its source and an event key together.

- Posting the same snapshot again is a no-op.
- Posting a changed snapshot for the same source and key replaces its earlier contribution to the aggregates. This is how local cumulative day and model snapshots are corrected safely.
- Observations with no event key are append-only.
- A source that posts a corrected snapshot of zero removes that snapshot's contribution.

Local producers add a machine name to their source id, for example `codex-local@my-machine`, so that sweeps on different machines never overwrite each other. Because of this you may see one Data sources row for each machine. See [Data sources](/docs/data-sources#per-machine-local-sources).

A manual cost correction on an estimated, notional or `None` event rebases it to `Provider estimate` and stamps a correction marker. The marker stops a later replay that carries no cost of its own from rolling the corrected cost back to unknown.

## Why totals never mix

Adding a billed invoice to a list-price estimate to a notional value gives a number that matches no real quantity. Part of it was paid, part of it would have been paid, and part of it is a comparison. Observatory prevents the mistake in three ways:

1. **Separate cards.** Each basis has its own summary card with its own label and qualifier.
2. **Separate rows.** In the Model breakdown, the same model under two bases appears as two rows. Rows are grouped by provider, model, source, scope and basis together.
3. **Separate series.** In the `Usage value` chart you pick one value at a time, and each bar segment is one provider, source, scope and basis.

The generated insights follow the same rule: the prompt tags every figure with its basis and tells the model not to describe notional or estimated values as spend. See [Usage and insights](/docs/usage-insights#how-insights-are-generated).
